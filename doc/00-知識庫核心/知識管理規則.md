# 知識管理規則

本文件定義 `doc/` 目錄下所有知識文件的新增、修改與維護規則。任何對 `doc/` 的操作都應遵循以下規範。

---

## 1. 語言規範

- 所有內容**必須**使用**繁體中文**撰寫。
- 專有名詞、程式碼關鍵字、函式名稱、原文無適當翻譯之術語，可保留原文並以括號附加對照。
  - 範例：`依賴注入（Dependency Injection, DI）`、`快取（Cache）`
- 禁止使用簡體中文、注音文、火星文等非正式書寫形式。

---

## 2. 分類與歸檔規則

### 2.1 知識分類目錄

知識文件必須依其性質放入對應的分類目錄中。目前定義的頂層分類如下：

| 目錄 | 適用內容 |
|------|----------|
| `00-知識庫核心/` | 知識管理規則、分類標準、範本等管理知識庫本身的文件 |
| `01-開發技術/` | 程式語言、嵌入式開發、系統設計、資料庫等所有技術主題 |
| `02-開發工具與流程/` | Git、Docker、編輯器設定、CI/CD、開發工作流程 |
| `03-科普新知/` | 科學普及、新技術趨勢、跨領域知識、科普書籍筆記 |
| `04-人文閱讀/` | 文學、小說、散文閱讀筆記與心得 |

### 2.2 分類原則

1. **符合性優先**：新文件應先檢查現有分類中是否有合適的目錄。
2. **就近歸類**：若內容涵蓋多個分類，選擇最主要的那一個，並在文件中透過 `[[wikilink]]` 關聯到其他相關文件。
3. **新增類別**：若現有分類均不適合，可在合適的父層級下新增目錄。新增後必須同步更新本文件的「知識分類目錄」表格。
4. **一層原則**：目錄深度以 2~3 層為限，避免過深造成維護困難。

---

## 3. 新增與合併規則

### 3.1 新增前檢查

新增任何文件前，必須先執行以下檢查：

1. **全文搜尋**：使用關鍵字搜尋整個 `doc/` 目錄，確認是否已有相關內容。
2. **關聯檢查**：檢查 [[目錄結構與分類標準]] 中定義的分類，確認是否已有相似主題文件。
3. **交叉比對**：透過 Obsidian 圖譜（Graph View）檢視相關文件之間的連結關係。

### 3.2 合併原則

若發現已有相關內容：

1. **優先整合**：將新增內容整合到現有文件中，而非另開新檔。
2. **禁止刪減**：除非特別要求，否則整合時**不得移除或刪減**原有內容。僅能補充、擴充或重組。
3. **附加保留**：若為觀點補充或不同面向的探討，應以新增章節（Heading）的方式附加，保留完整脈絡。
4. **連結取代複製**：若兩份內容高度相關但主題明確可分，應使用 `[[Page Name]]` 或 `[顯示文字](path/to/file.md)` 進行關聯，避免重複撰寫相同內容。

### 3.3 衝突處理

若新增內容與既有內容觀點不一致：

1. 在文件中並列呈現不同意見，標註各自來源或背景。
2. 使用 `> [!NOTE]`、`> [!WARNING]` 等 Obsidian Callout 來標示爭議或待確認事項。
3. 勿擅自刪除或覆蓋他人撰寫的內容。

## 4. 文件拆分規則

當文件經過多次擴充，可能出現內容過多、結構複雜或主題偏離的情況。本章節定義文件拆分的判斷指標、執行流程與後續處理規範。

### 4.1 拆分判斷指標

以下指標可作為是否需要拆分的參考依據：

#### 4.1.1 內容量化指標
- **行數**：文件總行數超過 300 行
- **章節數量**：二級標題（`##`）超過 10 個
- **段落密度**：單一章節內容過長（超過 100 行）

#### 4.1.2 結構複雜度指標
- **主題分散**：文件涵蓋 3 個以上獨立主題
- **關聯性低**：不同章節間缺乏明確關聯
- **維護困難**：修改某部分時容易影響其他部分

#### 4.1.3 主題偏離指標
- **附屬內容過多**：背景知識、歷史沿革等附屬內容超過主旨內容
- **跨界探討**：包含與主旨無直接關聯的跨領域內容

### 4.2 拆分觸發條件

拆分可由以下方式觸發：

1. **定期檢視**：每季度或每半年對知識庫進行結構性檢視
2. **編輯時檢測**：編輯文件時，若發現符合上述指標，應考慮拆分
3. **主動評估**：撰寫者或維護者主動評估文件結構

### 4.3 拆分執行流程

#### 4.3.1 規劃階段
1. **主題分析**：分析文件內容，識別可獨立的主題區塊
2. **拆分方案**：規劃拆分後的文件結構與關聯方式
3. **影響評估**：評估拆分對其他文件的影響

#### 4.3.2 執行階段
1. **建立新文件**：為每個獨立主題建立新文件
2. **內容遷移**：將相關內容遷移到對應的新文件
3. **建立關聯**：在原文件與新文件之間建立 `[[wikilink]]` 關聯
4. **更新導航**：在原文件保留摘要或目錄，確保導航完整

#### 4.3.3 驗證階段
1. **內容完整性**：確認所有內容已正確遷移
2. **關聯正確性**：確認所有關聯連結正確無誤
3. **格式合規性**：確認新文件符合格式規範

### 4.4 拆分後處理

#### 4.4.1 文件規範
- 新文件必須包含完整的 YAML frontmatter
- 檔案名稱應反映內容主題，遵循命名規則
- 必要時更新分類目錄

#### 4.4.2 關聯維護
- 原文件應保留簡要摘要或目錄
- 使用 `[[wikilink]]` 建立明確關聯
- 必要時更新其他相關文件的連結

#### 4.4.3 知識庫更新
- 更新「目錄結構與分類標準」（如有新增分類）
- 在變更歷程中記錄拆分操作

### 4.5 範例說明

#### 4.5.1 案例一：技術文件拆分
**原文件**：`嵌入式系統開發.md`（包含硬體介面、驅動程式、作業系統、開發工具等多個主題）

**拆分方案**：
- `嵌入式硬體介面.md`（硬體介面相關內容）
- `嵌入式驅動程式開發.md`（驅動程式開發）
- `嵌入式作業系統.md`（作業系統相關）
- `嵌入式開發工具.md`（開發工具與環境）

**關聯處理**：
- 原文件保留簡要摘要與各子文件連結
- 各子文件之間使用 `[[wikilink]]` 關聯

#### 4.5.2 案例二：主題偏離處理
**原文件**：`Python 網路爬蟲.md`（包含爬蟲技術、資料庫儲存、資料視覺化、機器學習預測等）

**拆分方案**：
- `Python 網路爬蟲.md`（保留爬蟲核心內容）
- `爬蟲資料儲存.md`（資料庫儲存相關）
- `爬蟲資料視覺化.md`（資料視覺化）
- `機器學習基礎.md`（獨立為通用技術文件）

**關聯處理**：
- 各文件之間建立明確關聯
- 確保每個文件主題明確且自成體系

## 5. Obsidian 格式規範

因本文件庫使用 Obsidian 作為閱讀工具，所有 `.md` 文件必須遵守以下格式：

### 5.1 Frontmatter（後設資料）

每個文件開頭必須包含 YAML frontmatter：

```yaml
---
title: 文件標題
tags:
  - tag1
  - tag2
created: YYYY-MM-DD
modified: YYYY-MM-DD
aliases:
  - 別名1
  - 別名2
---
```

- `title`：文件標題（必填）
- `tags`：標籤清單（建議填寫，用於分類篩選）
- `created` / `modified`：建立與修改日期（格式 `YYYY-MM-DD`）
- `aliases`：別名（選填，便於透過不同名稱連結到此文件）

### 5.2 內部連結（Wikilinks）

- 檔案間連結使用 `[[檔案名稱]]` 或 `[[檔案名稱|顯示文字]]`。
- 連結到特定標題：`[[檔案名稱#章節標題]]`。
- 嵌入其他檔案內容：`![[檔案名稱]]`。

### 5.3 標籤（Tags）

- 文件內可使用 `#tag` 進行標記。
- 標籤建議使用英文或英文+數字，避免中文標籤的路徑編碼問題。
- 建議 tags 層級：`#area/技術`、`#topic/嵌入式`、`#status/進行中`。

### 5.4 Callout 提示區塊

使用 Obsidian Callout 格式標註特殊資訊：

```
> [!NOTE] 一般提示
> 補充說明或注意事項

> [!WARNING] 警告
> 需要注意的潛在問題

> [!TIP] 技巧
> 實用建議或最佳做法

> [!IMPORTANT] 重要
> 必須遵守的關鍵事項

> [!CAUTION] 小心
> 可能導致錯誤的操作
```

### 5.5 程式碼區塊

所有程式碼範例必須使用圍欄式程式碼區塊（fenced code block），並標註語言：

````
```python
print("Hello")
```
````

### 5.6 檔案命名規則

- 檔案名稱應簡潔且具描述性。
- 使用全形字元（中文）或連字號 `-` 連接英文單字。
- 避免使用空白、特殊符號。
- 範例：`快取策略.md`、`api-authentication.md`

---

## 6. 例外與豁免

- 若因特殊原因無法遵守上述規則（如引用外部原文資料、自動產生的文件等），應在文件 frontmatter 中加入 `exempt: true` 並於首行說明原因。
- 任何規則修改須經團隊討論決議，並在此文件記錄變更歷程。
